# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A HACS custom integration for [Comexio IO-Server](https://www.comexio.com/) — a local building-automation controller. It exposes Comexio Markers and physical IOs as Home Assistant entities, and manages a "Web-IO" webhook class on the Comexio server so it can push live values back to HA.

- **HACS domain:** `comexio`
- **IoT class:** Local Push (webhooks from Comexio → HA)
- **Minimum HA:** 2026.10.0
- **Python:** ≥ 3.12

## Code quality rules

- Line length: 120 (see `pyproject.toml`)
- Ruff rule sets: B, C4, E, F, I, SIM, UP, W, plus the Sourcery-style refactoring sets FURB, PERF, PIE, PLE, PLW, RET, RSE (PLR/TRY left out as noise), plus PT012/PT018 (one statement per `pytest.raises`, no composite asserts — SonarCloud S5778/S9073). PT012 misses a nested call (`check(build(x))`); `tests/unit/test_pytest_raises_single_call.py` enforces one call per `pytest.raises` block
- Sourcery enabled for all files except `.github/` and `tests/`
- Cognitive complexity ≤ 15 as SonarCloud measures it (S3776), for every function; no duplicated string literals (extract constants). `tests/unit/test_cognitive_complexity.py` measures it with complexipy before the push. complexipy scores close to but not exactly like SonarCloud, so the one permitted exception is its `BASELINE`: functions SonarCloud accepts but complexipy already rated above 15, pinned at that score — lower or drop an entry once the function is simpler, never add one for new code
- **Tests alongside ruff:** every change runs `pytest tests/unit` (and, for HA-facing code, `pytest tests/ha` in WSL) in addition to `ruff check` / `ruff format` before it counts as done (the pre-commit hook `pytest-unit` and the CI job `tests` enforce the same). A red test is a finding, not an obstacle — never delete or loosen an assertion to make it pass.
- **Snapshots:** a failing snapshot means the output changed. If the change is intended, regenerate with `--snapshot-update` and state the reviewed snapshot diff in the PR; otherwise fix the code.
- **Coordinator test doubles:** a stand-in that binds real coordinator methods (`name = ComexioCoordinator.name` in a `_FakeCoordinator`) must also supply every coordinator method those methods call on `self`. `tests/unit/test_fake_coordinators_bind_what_they_run.py` fails otherwise, naming the missing one: bind it, mock it, or list it in its `ALLOWED` with the reason. It reads class-based doubles only; a `SimpleNamespace` handed to `ComexioCoordinator.method(fake)` stays the reviewer's job
- **Regression tests:** every bug fix in pure logic (parsers, command builders, diff/render/analysis) gets a test that fails without the fix. Test data goes to `tests/fixtures/comexio/` and must be synthetic.

## Terminology: "function plan"

One concept, three historical names — the rules are:

- **function plan** — the canonical English term everywhere: code identifiers (`function_plan_*` / `FUNCTION_PLAN_*` / `FunctionPlan*`), services, entity names, repair dialogs, notifications, logs, README (EN), en/fr/es translations. It matches Comexio's own FUP/FUB vocabulary (`run_fup`, `fub_id` — Funktionsplan, IEC 61131-3 Function Block Diagram).
- **Logikplan** — the correct German *translation* only: `de.json` and the German README section. Never in English UI text or code.
- **`logikplan_*`** (lowercase German spelling) — frozen legacy spelling of *persisted* identifiers: the five option keys in `const.py`, the `Store` storage keys (backup + catalog), and the plan-selector unique_id `comexio_{server_id}_logikplan_plan_selector`. Never rename these without migration code.
- The former internal code name `logicplan` was fully renamed to `function_plan` (2026-07); do not reintroduce it.

## Architecture overview

All integration code lives in `custom_components/comexio/`.

### Data flow

```
Comexio IO-Server
    │  RSA login (admin session)          GET /admin/function_function_module/home
    │  Live states (markers)              POST /board/dashboard/refresh/
    │  Web-IO write/delete (sync)         POST /admin/web_io/...
    │  API write (values)                 GET /api/?action=set&...  (Basic Auth)
    │
    ▼
ComexioAPI (api.py)
    │  parse_config()  →  markers[], io[], webio_commands{}
    │
    ▼
ComexioCoordinator (coordinator.py)   ← DataUpdateCoordinator
    │  _async_update_data() polls on schedule (default 15 min)
    │  Smart Audit: compares HA entity map vs. Comexio Web-IO commands
    │    → creates HA Repair issue if mismatch detected
    │  update_marker() / update_io_by_name()  ← called by webhook handler
    │
    ├── Entities: sensor / switch / number / button / binary_sensor
    └── Webhook: POST /api/webhook/<id of the command>  ← push from Comexio (one HMAC-derived id per Web-IO command;
                the old comexio_{server_id} stays registered only until the migration is verified, see below)
```

### Comexio data types

- **Markers** (`FubModules["2"]`): server-side state variables (digital or analog). Live values fetched via dashboard refresh endpoint. IDs are integers; webhook payload `{"type": "marker", "id": "...", "value": ...}`.
- **IOs** (`FubModules["1"]`): physical inputs/outputs on extension modules. Whether binary or analog is determined by `$ioTypes` (scraped from admin page). Webhook payload `{"type": "io", "ext": "...", "io": "...", "value": ...}`.
- **1-Wire sensors** (`FubModules["12"]`, plan element type 12 with `ref_id` = config id): read-only, keyed by their address (`OT1`); values arrive **only by push** from the Web-IO class `<name> [1Wire]` (plans `{prefix} - 1Wire [1-100]`, range-clustered like markers) — never poll them. Only their status (read error / not found, `api.get_onewire_status()`) comes with the config poll and drives availability plus the `onewire_problem` sensor. Webhook payload `{"type": "onewire", "id": "<address>", "value": ...}`; the webhook dispatch keys pushes by address, not config id (config ids repeat across prefixes).

### Two authentication paths

- **Admin session (RSA):** `api.login()` — uses RSA PKCS1v15 to encrypt credentials, stores the cookie. Required for config scraping and Web-IO management.
- **API (Basic Auth):** `api.set_value()` — used for writing values to markers and IOs. Configured separately via `CONF_API_USERNAME` / `CONF_API_PASSWORD`. Exception: since aiocomexio 0.9.0 only the digital outputs `Q*` and `DG*` go over `/api/`; every other IO (the analog outputs `AO*`, which `/api/` answers with `Forbidden`, but also `AI*`, `QI*`, …) is written over the admin session — `set_value` asks `aiocomexio.io_written_over_admin_session` (#259).

### API write retry (`ComexioAPI.set_value`, #289)

A write over `/api/` (markers, KNX objects, `Q*`/`DG*`) that failed because Comexio closed the connection before answering (`ComexioConnectionError` caused by `ServerDisconnectedError`) is sent again — at most `API_WRITE_RETRY_MAX` (3) times, only while each drop came back within `API_WRITE_RETRY_WINDOW_SEC` (0.5 s; later Comexio may have taken the command), only while HA's own value of the target (`coordinator.cached_value`) has not changed since the write was issued (`api_write.held_value_objection`: a push of the wanted value means Comexio took it, a push of another value is newer and must not be overwritten; a value that was there all along proves nothing, a stale one included; a caller passes `even_if_held=True` where the write has to go out whatever HA's value does: a DPT3 stop), and never for a write that toggles or moves by a step (`repeat=False` from `ComexioMarkerTriggerButton`: its plan input toggles on every write; and from `ComexioKnxDpt3Entity` for a DPT3 step code 1–7, a relative move — the stop code 0 stays repeatable). Writes to one target run one after the other (`_write_locks`, keyed by `_write_target_key`: `5`, `"5"` and `"05"` are one marker), so a repetition of an older write never lands after a newer one. The connection settings the write depends on (`write_settings`: host, pinned certificate and the user of the way it goes — the API user for `/api/`, the admin user for the admin session) are taken when the write is issued: once a reconfigure changed them, a write still waiting or due for a repetition is not sent to the new ones and fails; a repetition that is not sent is not counted. The dimmer (`ComexioKnxLight`) binds a move and its stops to the same settings (`_async_stop`): a stop is not sent to a server the entry was reconfigured to meanwhile, the error then says the actuator may still be moving. The 0.5 s is measured from the send of the attempt; a wait behind another request in aiocomexio counts, which only errs on the safe side (no repetition). A drop that is not repeated because HA's value changed is still reported as failed; its error line names the reason, as for changed connection settings. The window is an assumption, not a measurement: a local Comexio answers in milliseconds, so a quick drop can also come after the command ran, and a repetition of a marker that pulses or toggles on every write could then act twice. Nothing else is repeated (the admin-session path `AO*` has aiocomexio's own retry). Every failed write (`set_value` returning False, whichever way it goes: `/api/` or, for an IO like `AO*`, the admin session), retry and rescue is counted in `ApiWriteStats` (`api_write.py`, in memory, reset on restart) and shown by the diagnostic sensor "API write errors" (count of failed writes; attributes `retries`, `recovered_by_retry`, `last_failures` with time, target and error class). Keep the conditions in step with `tests/unit/test_api_write_retry.py`.

**API settings check after a failed `/api/` write:** a write over `/api/` (`ComexioAPI._written_over_api`: markers, KNX, IOs not written over the admin session) that finally failed without a clear answer (`api_write.worth_diagnosing`: `ComexioConnectionError` i.e. timeout or drop, HTTP error status except 403, `ComexioDataError`) reads Comexio's API page once (`client.get_api_settings()`, admin session, no login, no second try, its own limit `API_SETTINGS_CHECK_TIMEOUT_SEC` = 10 s) in `ComexioAPI._diagnose_failed_write`, after the last attempt and before the failure is logged and counted. Only the sends hold the target's lock (`_send_until_done`); the read, the log line and the counter come after it (`_report_failed_write`), so a DPT3 stop never waits for a read of up to 10 s — pinned by `test_the_look_at_the_settings_does_not_hold_back_the_next_write_to_the_same_target`; the line of an older failed write may therefore follow a newer write to the same target. The text (`api_write.api_settings_diagnosis`: API switched off, marker/IO access read only or forbidden, single selection without that marker released, login user or password differs; or "do not explain it" with `ApiSettings.summary()`) goes into the error log line, into `ComexioAPI.last_write_diagnosis` (a ContextVar like `last_write_met_another_certificate`, read right after the write) and from there into `entity.write_failed` and the `set_value` service notification. A refusal ("Forbidden" / 403 / rejected login), a certificate mismatch, a session that is gone (unload, Home Assistant stopping: `_session_gone_reason`), an admin-session write (`AO*`) and every write that went through read nothing. A page that cannot be read adds "could not be read (<reason>)" (timed out / admin session not logged in / error class, never the error text); the write's own error stays the one `ApiWriteStats` counts, so the sensor and its `last_failures` are unchanged — except a certificate mismatch the read itself meets: that is kept for the repair, set as the write's certificate cause and named by the counter, like one the write met. The read is best effort: any error but a cancellation becomes that note (an unexpected one, i.e. not `ComexioError`/timeout, also a warning with its class only), so the line and the counter are never lost; a cancelled caller still gets both (`finally`). The page holds the API password in clear text: aiocomexio compares it with the configured one and passes on only the verdict; neither it nor the page's user name may reach a log or message (`tests/unit/test_api_write_diagnosis.py` checks it with the synthetic `api_settings_page.html`). Writes that fail while a read is under way share it (`_shared_settings_read`, shielded; Comexio serialises requests, so a burst of failures must not queue one page read each); a read that is over is not reused (no cache), nor one started under other connection settings (a reconfigure came in between). A certificate mismatch of a shared read is kept once (`_mismatch_noted_read`), but every waiting write names it as its cause. What a read found is dropped when the connection settings changed meanwhile (text and mismatch belong to the old server). A read that ends with the session (unload, Home Assistant stopping) adds no note. A caller that sends a stop the moment a failed write returns passes `diagnose=False` (the dimmer's DPT3 move, `ComexioKnxLight._async_start_move`; the failure is logged and counted as always, `last_write_diagnosis` stays empty). Keep in step with that test.

### Sessions and keep-alive (`http_session.py`, #289)

Comexio closes an idle connection after about 6 s, aiohttp keeps one for 15 s; a request sent in between meets the close ("Server disconnected", 6.6 % of the POSTs in the measurement of 2026-11-11). The keep-alive is a connector setting and `async_create_clientsession` always uses Home Assistant's shared connector, so every session to Comexio (main and preview) comes from `http_session.async_create_session`: a `ComexioConnector` of its own with the keep-alive of aiocomexio's `connector_kwargs()` (3 s, since 0.14.0; the number and the reason live there), built like Home Assistant's (its TLS context, its User-Agent, and its DNS resolver, the one that answers `.local` names over zeroconf). The resolver has no public accessor (`aiohttp_client._async_get_or_create_resolver`); where it is missing, the session is Home Assistant's own and a warning says so once. `discard_session` only detaches such a fallback session, as Home Assistant itself does: the shared connector stays open and no close timer is set (pinned by `test_discarding_the_fallback_session_leaves_home_assistants_shared_connector_open`). A session is dropped only with `discard_session`, never `close()`: it detaches (a request in flight finishes, a new one fails) and closes the connector `COMEXIO_HTTP_TIMEOUT_SEC` + 5 s later, or at once when Home Assistant stops. A session that never got into use (a failed preview login) closes at once (`unused=True`). Only the main session is bound to the entry (`bind_to_entry=True`); the preview session, replaced with every lapsed login, would leave a callback on the entry each time. Closing right away would cut a request off with "Server disconnected", which aiocomexio and the write retry would take for Comexio's drop. The write retry stays the safety net; after `ComexioAPI.close()`, and once Home Assistant stopped (its CLOSE event closes the connector while the entry is still loaded: `session.closed`), no write is sent any more, a repetition included (`ComexioAPI._session_gone_reason`). The periodic reads (bus load every 10 s, uptime, function plan run states, the preview connection-value poll) end quietly in the same case: `coordinator._skip_when_connections_closed` skips a tick on a gone session (`ComexioAPI.session_is_gone`) and swallows aiohttp's `RuntimeError("Session is closed")` only when `met_the_closed_session` confirms the session is gone — before, Home Assistant logged it as "Task exception was never retrieved" at a stop that hit a tick (open point eh). The preview poll catches its own errors, so for it the decorator only skips the tick and its own `except` returns without counting a failure only when `ComexioAPI.read_ended_with_the_session` says the request ended with the session (aiohttp's refusal, or a transport error / `aiohttp.ClientConnectionError` / timeout of the request in flight, the same rule as the settings read after a failed write; a response or payload error is still counted); every other error is still counted and logged. The run-state fetch (`_async_refresh_plan_run_states`) does the same for a transport error or timeout, which its own `except` would otherwise count as an outage (warning, `note_comexio_unreachable`); the helper `_async_count_run_state_fetch_error` also ends quietly on aiohttp's refusal itself, because `async_plan_transition` and `async_start_managed_plan` call the fetch without the tick's guard. The bus-load, uptime and free-storage reads swallow a transport error inside aiocomexio and hand back an empty reading, so the tick checks `api.session_is_gone` before it counts one: a read that ended with the session advances no fail streak and clears no valid reading. A regular refresh (`_async_update_data`) that meets the closed session returns the data it has (re-raised when there is none yet), so Home Assistant logs no "Unexpected error fetching" at the stop. Such a refresh counts no failed storage fetch (`_async_run_update` and `_async_refresh_system_info_storage` leave the system info alone when the session is gone), and a preview tick that waited for the preview lock, or whose preview login the stop overtook, opens or keeps no new session once the main one is gone (`ensure_preview_session`). The nightly ticks (firmware, range check, webhook migration) carry no decorator: they do not fire at stop. A periodic tick that reads from Comexio and runs at stop should get the decorator too; `tests/unit/test_ticks_closed_session.py` pins the four above. Keep this in step with `tests/unit/test_http_session.py`.

### Sync strategy (button.py)

The sync button (`ComexioSyncButton.async_handle_press`) chooses between two strategies:

- **Delta-Sync:** Targeted create/rename/delete/type-fix of individual Web-IO commands via `save_single_command` / `delete_single_command`. Used when action ETA < `SYNC_DURATION_RECREATE` (~79 s).
- **Full-Recreate (Fast-Track):** Deletes entire device + class, uploads fresh JSON template via `upload_web_io`, then creates device instance. Used when Delta ETA > threshold *and* device is not linked in Comexio logic.

The coordinator's `last_audit_results` dict (populated every poll) drives both strategies. The sync lock (`_sync_lock`) prevents concurrent runs.

**Wiring stages after a sync (`_wire_plans_after_sync`, #333):** the stage list is `[plan pairs, KNX (inserted at index 1), trigger pairs]`; `_run_wiring_stages` checks `cancel_sync` before each stage and records the ones a cancel skipped (`ctx.skipped_stages`, the "Not started" banner). Without the KNX import (`WebioClass.KNX` not in `active_webio_classes`) the KNX stage is not part of the run, so there is no "Checking KNX write path and wiring..." status and the cancel banner does not list it — except when this sync created KNX commands (`_created_knx_ids`, read from the command name): their read path still needs wiring. That decision is made once, when the list is built. Which gaps the stage takes is decided when it starts (`_wire_knx_stage`): with the import on every gap, with it off only those of the KNX commands this sync created. `active_webio_classes` is live, but the guarded reload waits for the running sync, so a switch mid-sync only moves the gap filter, never the stage list. Known limits (not measured live): a KNX naming schema without `K{KnxId}` gives a created command no id in its name, so the import being switched off mid-sync leaves its read path unwired in that sync; and an import switched on after the list was built brings the stage in only with the next sync. Keep in step with `tests/unit/test_sync_ha_address_guard.py` and `tests/unit/test_fresh_mid_sync_audits.py`.

**Rename, type change and rewiring in one sync (#332):** Comexio cuts the plan connection of a marker or IO whose type changed, so a source can be renamed, retyped and unconnected at once. The debris check (`_function_plan_dangling_items` / `_dangling_io_items`, fed by `_dangling_source_ids` = `{ref_id: [fub_ids]}`) therefore spares the one unconnected element of a source whose Web-IO command has a wiring gap (`wiring_gap_keys`, the audit keys `M220`, `QB211`, `IO_Ext1_I1`; `_closed_by_rewiring`: `key in wiring_gap_keys and len(fub_ids) == 1`): the wiring pass of the same sync reconnects it, where the cleanup would have deleted it and the gap would have been found only by the next poll. A source with several unconnected elements is a duplicate and stays debris. A gap whose command still waits for its rename carries `pending_rename` (`_compare_audit_key`): the pair writer finds a command by its new name, so only `full_sync` wires it, after the rename (`button._gap_items_for_action`; every other action drops these gaps). Known limits (a follow-up, not yet fixed): the check counts unconnected elements per `ref_id`, not per element and plan, so an unconnected duplicate next to a connected element is not reported and a lone unconnected element in a managed plan other than the one the pair writer writes to is spared although the writer will not reuse it; each only delays the cleanup by one sync. Keep in step with `tests/unit/test_rewire_after_rename.py` and `tests/unit/test_audit_maps.py`.

Column plans — IO extensions (`{prefix} - IO [A,B]`, option `logikplan_io_extensions`) and Quickbus devices (`{prefix} - QB [1,3]` by device id, option `logikplan_quickbus_devices` holds device ids) — run on one machinery parameterized by `const.IoPlanKind` (`IO_PLAN_KIND_IO` / `IO_PLAN_KIND_QUICKBUS`): 50/100/150 pairs per plan → 1/2/3 columns, deterministic rows (`column_blocks`), no sort pass. An extension takes a column of its own; Quickbus devices (`stacked`) fill a column top to bottom, one blank row apart, and a device joins the first plan whose columns still hold it — `const.io_plan_member_origins` gives every member its (column, row) and is shared by the wire path and the grid/sort code. `coordinator.managed_io_groups()` is the single source of which `(kind label, member)` pairs are wired (opted in, online; a selected Quickbus device that is gone or on an offline extension is skipped). Users see a Quickbus member as `QB3 MT1` (`IoPlanKind.member_label`). The Quickbus selection defaults to every device while the option was never saved (`const.selected_quickbus_devices`), and only selected devices get Web-IO commands (`webio_quickbus_ios` / `coordinator.webio_source_data()` feed the audit map, the Web-IO builders and `required_webio_classes`) — an unwired Quickbus command would push nothing. Quickbus IOs are wired only (Comexio → HA): the Comexio API answers `Forbidden` to Quickbus writes.

### Device names

Sub-devices are tagged by kind so each kind lists together (`const.extension_device_name` / `quickbus_device_name` / `marker_device_name`): `<server> BASE` (onboard IOs, no tag, matched case-insensitively), `<server> EXT - <ext>`, `<server> QB - <device>` (linked via_device to its host extension's device once that exists, else to the hub), `<server> Markers` (no tag), `<server> 1-Wire` (`const.onewire_device_name`, no tag). Plain letter tags, no brackets: the HA frontend sorts with ICU, where `[` would sort before `#` and push `<server> # Function plans` away from the hub. Device names are display only — identifiers stay `{server_id}_{ext}` / `{server_id}_qb{device_id}`. An entity whose entity_id HA derives from its device name must not pick up a tag: the extension firmware entity requests its pre-tag id `const.extension_firmware_object_id` (`update.{server}_{ext}_firmware`).

### Entity naming (configurable)

Both `schema_marker` and `schema_io` are `str.format_map(SafeDict(...))` templates. `SafeDict` (in `aiocomexio.config`) leaves unknown `{keys}` unchanged. Default schemas:

- Marker: `"M{MarkerId} {MarkerTitle}"`
- IO: `"{IoId} {IoTitle}"` — no `{ExtName}`: IO entities sit on one device per extension and use `has_entity_name`, so the friendly name is already "`<server> EXT - <ext>` + entity name" (`<server> BASE` for the onboard IOs). The old default `"{ExtName} {IoId} {IoTitle}"` (`LEGACY_DEFAULT_SCHEMA_IO`) is pinned into config entries that never saved a schema (entry migration 1.2 → 1.3), so existing installs keep their names.
- Available placeholders: `ServerAlias`, `MarkerId`, `MarkerTitle`, `ExtName`, `IoId`, `IoTitle`
- An unnamed marker, and an IO whose description is empty or merely repeats its identifier, gets the title `#nn` — the title is never empty, so no schema renders an empty name or a dangling separator. Accepted limit: a schema of only `{IoTitle}` names all unnamed IOs of an extension `#nn`.

### Webhook ids (dg)

Every Web-IO command pushes to an id of its own: `derive_webhook_id(secret, command_key)` (HMAC-SHA256, 32 hex chars). The secret and the migration ledger live in a `Store` keyed by the entry id (`webhook_security_store`), never in the config entry. The handler accepts a request only if `WebhookSecurity.accepts(id, payload)` holds (the id belongs to the payload's command, `server=` matches the entry); the old id `comexio_{server_id}` is accepted only while `legacy_enabled`.

- **Migration:** the nightly tick (01:30, `_async_webhook_migration_tick`) rewrites each command's path and `server=` field (address stays as it is; the protocol follows Home Assistant's target, see the protocol bullet below). The old id is switched off only when every command is in the ledger, Comexio has restarted after the last write (`_restart_pending`: Comexio sends a changed command only after a restart) **and** a read-back of every command confirms path and body (`command_deviation`). Only a write of a path, server field or protocol of an **existing** command moves `last_write`: a new command (`created`) and a plain same-type, same-protocol rename of a command already in the ledger (`replaces`, from the audit's `previous_name`) push at once without a Comexio restart (measured 2026-11-22, with `[M]` marker commands only: the other classes save through the same endpoint, but a new `[IO]`/`[KNX]`/`[QB]`/`[1Wire]` command was not measured on its own), so `mark_written` leaves the stamp alone for them (pinned by `tests/unit/test_webhook_restart_stamp.py`), except when the same write changes the protocol of a name the ledger knows (the old name's for a rename, also for a created command that reuses a name): that stamps. A rename carries the old name (`replaces`) and its protocol state (`https_written`, a pending `protocol_moved` proof) moves to the new name and is gone under the old one (the old name leaves `migrated` too, so a later command that takes the name over is a new one, not a known one that changed protocol); a rename that is part of an exchange of names within one sync (two commands swapping, or A to B together with B to C: `coordinator._flag_contested_renames` sets the audit item's `rename_contested` from the renames of the sync themselves, so an orphan or a create that wants a name is no exchange; `contested` of `save_single_command`) cannot move state name by name, because the writes run one after the other and the first would take or drop what the second still has to read, so `WebhookSecurity._mark_contested` moves and retires nothing, keeps both names known, makes both owe the proof where either may have carried HTTPS (a name already in `protocol_moved` counts) and stamps like a rewrite (a superset: at worst one more restart notice, never a lost proof); a rename that changes the type too (`rename_changes_type` of the audit item, `type_changed`) saves a new body and stamps like a rewrite. A write that moved the stamp awaits the ledger's save (`ComexioAPI._async_save_moved_stamp`; a failed save is logged and left to the delayed one), so a stored `restart_free` outlives it only for the time between Comexio's answer and that save. The audit does not read a command's form, so a rename that also corrects a path or body drifted outside the integration is not told apart from a plain one (the integration never detects such drift outside the migration's read-back); a ledger that holds commands but no stamp persists that as `restart_free`, or the load rule would stamp it "now" after a reload. The nightly rewrite, type fix, range correction and class upload still stamp. Do not shorten that chain; the exceptions are the writes named above that leave the stamp alone (a new command, a plain rename) and a Comexio that has no Web-IO device at all, where there is nothing to restart or read back (see the next bullet).
- **A new entry never has the old id on (ei):** a new store starts with `legacy_enabled = True` for the commands of an installation from before the per-command ids, but `coordinator._async_settle_legacy_webhook_id` switches it off (and persists that) at the first scraped poll of an entry that had no saved config at its setup (`_never_polled`, set in `async_seed_saved_onewire_sensors`; an unreadable store does not count) and whose poll read `$WebDevices` without a device of this entry (`_own_web_device_count == 0`, set in `_async_fetch_parsed_config` by `count_own_web_devices`: only devices of this integration count — `<webio_name> [M]/[IO]/[KNX]/[QB]/[1Wire]` under any base name, compared without blanks and case, and the pre-split `<webio_name>`; a Web-IO device of the user's own holds no command that pushes to our id and does not keep the old id on (ek), nor does the KNX loopback device, which writes to the Comexio API; an entry in `$WebDevices` without a readable `Name` makes the count `None`, never 0; a device of ours the user renamed in Comexio is not managed, audited or rewritten by the integration either, so it is not counted), with an empty ledger and no `last_write`. The proof is the list without a device of ours, not an empty `webio_commands`: that holds only the integration's own classes and is empty too when `$WebDevices` or group `"10"` was not decoded, or the commands sit in a pre-split or foreign-named device. A poll that did not read `$WebDevices` (`None`) decides nothing and leaves the flag set for the next one; a failed save keeps it set too (retried at the next poll of this run only: the config is saved after every scraped poll, so after a restart the entry counts as polled and keeps the old id, the safe side). It runs before the config is saved, so a crash in between leaves the old id on, never off by mistake. Any other entry (saved config, a Comexio with a Web-IO device of ours, a recorded write, a store recorded for another host: `WebhookSecurity.host_changed`, set by `_async_adopt_host` and persisted in the ledger, so a restart before the first scraped poll keeps it; it stays set, as it only matters while the entry has no saved config) keeps the old id for the migration. The poll must be a scraped one (`_last_poll_scraped`, `$FubModules` not empty): a real Comexio never has it empty (`$FubModules["5"]` is the block-type catalog), and the integration treats an empty one as a failed scrape everywhere else. Pinned by `tests/unit/test_webhook_security_flow.py`.
- **The migration never ends silently (ej):** besides (ei), the nightly run switches the old id off when the last poll read `$WebDevices` without a device of ours and the entry rewrote or wrote nothing (`_legacy_webhook_id_unneeded`, `_async_finish_without_stored_commands`: an entry that never synced), and where it stays on a repair says what holds it: `webhook_commands_stuck` (commands with no command or device id, `_report_unrewritable_webhooks`; a sync recreates them) and `webhook_restart_needed` (beside the notification, `_notify_webhook_restart`). Both are deleted when their cause is gone or the old id is off (`_clear_webhook_migration_notices`); they name command names only, never an id. They are not persistent, so `_restore_webhook_migration_notices` raises again, once per start, whichever of them is still due (the stuck repair only while commands cannot be rewritten, the restart repair and notification only while `_restart_pending`), from the uptime readings (`_async_system_info_tick`) on: the stuck repair needs no boot time, and with commands left to rewrite there is no restart to ask for, so it is raised as soon as the stocktake is readable; the restart repair and notification wait for the first reading that gives Comexio's boot time (before that `_restart_pending` takes an unknown boot time for a restart still to come and would raise the restart repair on every start). It reports only (same stocktake as the nightly run, nothing is rewritten or switched off) and waits (a failure counts as not done and is tried again at the next reading, `WEBHOOK_RESTORE_ATTEMPTS` times in all, then left to the nightly run) while there is no data or the entry unloads or `_webhook_stocktake_readable` says no: a poll is under way (`_polls_open`: the whole of `_async_update_data`, its awaits after the fetch included, because the scrape flags are set before `self.data` is) or failed, `$WebDevices` was not read, or the ledger names commands the data does not have. With the old id off it takes the migration's repairs and notification back before it counts as decided (a run cancelled after persisting the switch-off leaves them standing in a reloaded entry), and a switch-off whose save fails (`_async_switch_legacy_webhook_id_off`) opens the restore again, as a reading during that save saw the old id off. A start from the saved config runs no uptime reading, so a read-only entry raises nothing until the full setup that follows. Pinned by `tests/unit/test_webhook_migration_end.py`.
- **The protocol moves with the same machinery (#165):** Comexio's scrape shows no command protocol, so the ledger also holds `https_written` (names last written with HTTPS; any other command carries HTTP, as before HTTPS was supported), recorded in `ComexioAPI._note_command_written` from the payload's `Protocol` on both write paths (`save_single_command`, class upload). A command whose recorded protocol is not its target's (`ComexioCoordinator._protocol_differs`; the target's comes from `api.webhook_protocol`, resolved by `async_webhook_target`) is rewritten by the nightly run like one without its own path, and the run goes on after the old id is off while commands wait for the protocol, or `protocol_write` (set by `mark_written` when a command that already had its own path changes protocol; cleared when the read-back came out clean) is set. The read-back adds `protocol_deviation` (a deviating command leaves the ledger) and `protocol_unproven` (a form without a protocol field is unreadable, not deviating, where the target is HTTPS; HTTP targets are not blocked by it). The restart request and its repair cover both reasons, `_restore_protocol_restart_notice` raises it again after a start while only the protocol move is open. `press_action` `webhook_migration` (`async_force_webhook_migration`) clears the ledger's `migrated` and runs the tick now, outside the sync lock (the run takes it per command). The address sync of a device only changes the IP (`update_webio_device_address(..., keep_tls=True)`). Pinned by `tests/unit/test_webhook_protocol_migration.py`.
- **Never log or notify a per-command id or a payload from the endpoint** (it takes no authentication): refused requests go through `WebhookSecurity.warn_refused` (throttled, no payload), notifications through `redact_webhook_ids`.
- **The scan that enforces it:** `tests/unit/test_webhook_ids_stay_secret.py` reads every module of the integration as an AST and follows a webhook id or the secret (taint by name) into logging calls, `print`, `warn_refused`, notifications, repair placeholders and the text of a `raise`/`assert`; it also fails on a `WebhookSecurity(...)` built without the entry's host. A print that is safe anyway is listed in its `ALLOWED` with the exact call text and the reason (today only `handle_webhook`'s `_LOGGER.exception('Webhook Error: %s', e)`: the id goes to `security.accepts` and nowhere else; simulated 2026-11-09 with hostile payloads, no leak). An argument added to a listed call is a new finding.
- User docs: `docs/WEBHOOK_SECURITY.md` (EN + DE). Keep it in step with the flow above.

### Documentation layout

The guides (`BACKUPS`, `CONFIGURATION`, `FUNCTION_PLAN_PREVIEW`, `KNX`, `SUPPORTED_HARDWARE`, `WEBHOOK_SECURITY`) and their screenshots (`docs/assets/ui/`) live in `docs/`. `README.md`, `CHANGELOG.md`, `CLAUDE.md` and `info.md` stay in the root (HACS and GitHub read them there). `custom_components/comexio/orphaned_backups.py` links `docs/BACKUPS.md` by URL: move a guide only together with that link.

### Race-condition guards (see inline comments)

- **R1** (`coordinator.py`): Webhook updates arriving *during* a `get_raw_config` HTTP round-trip are preserved — coordinator clears dirty sets before the fetch, then prefers webhook values over stale API snapshot.
- **R2** (`__init__.py`, `button.py`): `_skip_next_listener_reload` flag prevents a double-reload when the sync button writes to `audit_ignored` in options (the explicit reload after sync is the canonical one).
- **R4** (`coordinator.py`): `_sync_lock` (asyncio.Lock) ensures only one sync run at a time.
- **Guarded reload** (`coordinator.async_reload_entry`): every reload of the entry goes through it — it skips the reload while a sync runs (the sync's closing reload covers it) and otherwise waits for `_sync_lock`, running restores and plan edits. HA's own `config_entries.async_reload` / `async_schedule_reload` would tear the coordinator down mid-sync or mid-restore; a use is allowed only where the guard cannot apply, listed with its reason in `ALLOWED` of `tests/unit/test_guarded_reloads.py`, which fails on any unlisted use.

### Registry scope

The entity and device registries hold the entries of every integration, and a unique_id is unique per integration only — a scan of a whole registry that matches on it can pick another integration's entry (#270). The integration therefore reads the registries through `er.async_entries_for_config_entry` / `dr.async_entries_for_config_entry`. Accessing `entities`, `deleted_entities`, `devices`, `deleted_devices` or the helpers that return foreign entries (`async_entries_for_area` / `_category` / `_device` / `_label`) is allowed only where a scan has to see more, listed with its reason in `ALLOWED` of `tests/unit/test_registry_scans.py`, which fails on any unlisted use.

### Repairs belong to their config entry

Every repair is raised through `issue_owner.async_create_entry_issue(hass, entry_id, issue_id, ...)`, never through `ir.async_create_issue` directly. From Home Assistant 2026.11 on it passes `config_entry_id`, so a repair is removed together with its entry; an older Home Assistant does not know the keyword, so it is left out there (detected on the signature, the HACS minimum stays 2026.8.0). A repair whose entry is already gone is not raised, only logged at debug level. `tests/unit/test_issue_owner.py` fails on a direct `ir.async_create_issue`, on the issue registry reached any other way than `ir.<attribute>`, on a lookup by a name built at runtime, on a wrapper call with another entry id than the one form each file reaches its own entry by, and on a second persistent repair. The KNX pre-release cleanup is the only persistent one; one raised before the link existed is never re-created with it, so `async_remove_entry` deletes it by id.

### GitHub Actions — HACS-spezifische Ausnahme

`home-assistant/actions/hassfest@master` und `hacs/action@main` **müssen** auf ihren Branch-Refs bleiben (kein SHA-Pinning) — weil Pinning die Validierung einfrieren würde. Die daraus resultierende SonarQube-Warnung S7637 ist als **"Safe"** in SonarCloud zu markieren.

### Translations

`translations/strings.json` is the authoritative source; `en.json`, `de.json`, `fr.json`, `es.json` mirror it. Add new translation keys to all files. The repair flow reads `hass.config.language` for inline strings not covered by the HA translation system.
